# 文档政策

## 信息取舍

事实依据按主题确定：wire 与格式以随文发布的规范和 schema 为准，当前支持状态以可复现的实现行为和验证结果为准，架构页记录当前职责与设计边界。旧版 native 实现只用于理解历史原因，不能定义当前系统。

`product-decisions` 是其声明范围内产品目标、需求、业务约束、领域决策、决策理由与行为契约的 Root Authority。每项产品判断只有一个权威定义。standard、concept、architecture 与 status 是下游消费者：它们可以摘要并导航到对应决策分支，但不得独立重定义这些判断，也不能以当前实现、验证状态或局部设计反向改写业务选择。

产品决策的分层、归约与变更闭环见[维护规则](../product-decisions/maintenance.md)。

只保留当前结论。需求、术语或设计发生修正后，直接更新为最终结果，不记录请求原文或纠错沿革。失效方案原则上删除；确有复用价值的错误经验，最多用一个短段落正向说明当前约束和适用边界。

## 决策理由

每个架构子系统可以保留一份决策理由页，记录满足产品承诺、领域语义和外部契约的实现取舍、复杂度预算和设计后果。业务选择及其理由由 `product-decisions` 唯一拥有；架构理由页如需说明影响，只能摘要并导航到对应决策分支。当前实现行为仍由 standard、schema、protocol、architecture 与 status 的对应权威页面定义；理由页不得复制字段表、状态机或支持结论，也不得覆盖这些页面。

临时 review ledger、实施计划、Phase、提交记录、旧验收清单和交接状态在决定闭环后退出长期权威。若某项理由只解释已经删除的中间方案，或其约束已被较新的设计取代，则直接删除；不要为保存重构过程把它改写成当前架构事实。

## 文档边界

- `standard`：语言无关的 wire、格式、schema、协议和一致性要求，应足以独立实现。
- `concept`：目标、边界、能力和主流程，不包含架构、算法或实现细节。
- `architecture`：职责、数据流、状态、所有权和关键算法，精确到具体逻辑即可。
- `future`：尚未实现的方向、进入当前设计的条件和主要风险。
- `status`：支持矩阵与已知问题，不重复标准或架构正文。
- `reference`：压缩后的历史经验，不描述当前系统。

除 standard、schema 和 protocol 外，优先写概括和导航。只有影响兼容、安全、所有权或正确性的细节值得进入正文。

## 写作规则

- 一个事实只设一个权威位置；其他页面摘要并链接。
- 当前、未来、历史和已知问题必须分开，禁止把计划写成已实现能力。
- 组件按职责命名，例如 Java 领域层、native 能力层和旧版 native 实现；不以本机工程目录名代指项目或架构角色。
- 稳定类名及少量关键函数、字段名可用于说明设计对象、架构边界、机制与逻辑；不得附源码路径、行号、成员清单，也不得以调用位置组织源码导览。
- 涉及 Minecraft、Forge 时优先直接使用正式符号（如 `VertexConsumer`、`level`、`entity`、`tick`），无需复述模组开发常识；YSM 原创且无法由 Minecraft、Forge 或通用领域术语推知的稳定名称必须在术语表统一释义。仅局部表达关键机制的函数或字段不扩成全局术语；standard、schema 或 protocol 已定义的局部 wire 符号也不重复收录。
- 使用相对链接；正式文档不得引用旧文档或本机路径。
- 不记录本机工程布局、IDE 工作区、检出路径、分支或 commit 信息、文档编写或更新时间，以及只对某次本地构建或核查有意义的临时元数据。
- 格式、缓存和协议均处于 unstable 状态时，必须明确说明，不使用“完全支持”“已经冻结”等绝对措辞。

正式文档必须自包含，不依赖已弃用资料才能解释当前系统。

验证投入与证据解释见[验证边界](verification-policy.md)；验收流程不作为产品判断节点，产品软目标也不能由验证流程反向重定义。
