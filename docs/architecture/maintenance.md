# 架构文档维护规则

按[文档政策](../governance/documentation-policy.md)确定信息归属；产品含义变化与冲突按[产品决策维护规则](../product-decisions/maintenance.md)裁决。归约以减少重复定义和检索成本为目标，不按篇幅删除正确性约束。

1. **先定唯一落点。** 沿 README 定位 owner，核对输入验证、成功发布和失败处置。产品承诺与理由保留决策引用；wire/格式引用标准；内部对象、算法与生命周期归所属机制页。跨层重复须一并收敛。
2. **先承接，再删除。** 比较重复段落的独有条件、顺序、身份、所有权、失败范围和例外，承接到唯一落点后，其他消费者只留必要摘要与精确链接。相似术语不证明机制相同，不能把不同阶段的完成条件合并。
3. **按页面职责压缩。** 总览保留职责、主数据流与问题路由；机制页定义执行规则；理由页只解释无法由设计直接推导的选择、成本和后果。图与正文只展开一次，删除公式直接推论、成员清单、重复否定和无额外约束的流程提醒。
4. **保留未闭合边界。** 当前构造与目标设计分别标明，差异和验证缺口引用既有状态记录；不通过删文把差异写成已解决。策略表、异常路径和非直觉约束须确认可从权威落点完整取得，才可归约。
5. **闭合引用并复核语义。** 审查候选写清删除范围、唯一落点、保留条件与成本；实施遵循已裁决范围。迁移时检索旧/新标题、路径和 ID，更新入站引用及受影响的 Landing/反向索引。结合 diff 确认独有含义未丢失、产品义务未改写，不保留长期去重台账。

完成后在文档根目录运行 `python tools/check_docs.py` 与 `git diff --check`；修改 Mermaid 时渲染校验，触及产品决策路由时另按其维护规则验证闭环。结构检查通过不证明语义完整或生产实现符合。
